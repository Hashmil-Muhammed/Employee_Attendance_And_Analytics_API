You will build the backend of a small HR attendance system: employees punch in and out, managers correct records, and the business asks questions of the data (who is late, which department is slipping, what does the trend look like). The data lives in MongoDB. You write the service in FastAPI.

5. Data model and conventions

MongoDB holds two collections, employees and attendance_logs. The grader seeds them directly, so your code must read them exactly as DATA_MODEL.md describes. That file lists every field and its type and includes nine sample documents. This section summarises what you need to keep in mind before you write any code.

Convention

What it means

Employee identity

emp_code identifies an employee everywhere. It is a customer-generated business code (for example EMP0001): unique, never changes, and not MongoDB's _id. _id is internal and never appears in a request or response. Attendance records have no id either; a record is addressed by (emp_code, date).

Instants

Every point in time in the API (punched_at, punch_in, punch_out, created_at, and the times in history) is an integer in epoch milliseconds. MongoDB stores them as BSON datetimes (UTC), so you convert at the boundary. Values that look like seconds, floats and strings are rejected with 422. By default PyMongo returns naive datetimes; decide how you will handle that.

Calendar values

Dates are YYYY-MM-DD (IST), months are YYYY-MM, and shift times are HH:MM (24-hour, IST), both in the API and in MongoDB.

Derived fields

work_hours, late_minutes, overtime_minutes and half_day are computed by your API and never sent by a client. They are stored, and analytics read the stored values instead of recomputing them.

Gaps in the data

Seeded records may omit history or half_day; treat them as empty and false. A weekday with no record at all is not the same as a record with status ABSENT.

Indexes

The seeded database has only the default _id index. Create the ones you need at startup.

What history is

history is the audit trail of manual corrections only: what the PATCH endpoint writes. Each correction appends one entry saying when it happened, who made it, why, and the before and after value of every field that actually changed. Punch-in and punch-out never write to it, and entries are never edited or removed. A record that has never been corrected has an empty history.

6. Business rules

These rules are repeated, with the same numbering, in openapi.yaml. They are intentionally not visible in the JSON schemas, so read them carefully; most wrong answers come from skipping one.

Rule

Statement

R1

Time zone and attendance date. Shift times and attendance dates are IST (UTC+05:30). A record's date is the IST calendar date of its punch_in. Overnight shifts (shift_end <= shift_start, e.g. 22:00 - 06:00): a punch-in earlier than shift_end belongs to the shift that started the previous day, and the shift ends on the next calendar day. Instants are truncated to whole seconds before any calculation, and the truncated value is stored and returned.

R2

Late. Grace period 10 minutes. Late only if the punch-in is strictly more than 10:00 after shift_start; then late_minutes = whole minutes (floor) since shift_start, not since the grace period ended. Shift 09:30: 09:40:00 gives 0; 09:40:01 gives 10; 10:15:59 gives 45.

R3

Overtime. Whole minutes (floor) from shift_end to punch_out, counted only if that is at least 30; otherwise 0.

R4

Work hours. (punch_out - punch_in) in seconds / 3600, rounded to 2 decimals half-up. null until punch-out.

R5

Half day. After punch-out, half_day is true when the rounded work_hours < 4.50. A half day counts as 0.5 of a present day.

R6

Presence. PRESENT, WFH, ON_DUTY count as present. ABSENT, LEAVE do not.

R7

Working days. Monday - Friday, no holiday calendar; counted from joined_on for mid-month joiners. present_days counts only Mon - Fri records; weekend records still add to late and overtime totals.

R8

Reported numbers. 2 decimals half-up (rates: 4 decimals half-up).

R9

Headcount. Employees with joined_on on or before the end of the period, whether or not they have any logs.

R10

Pagination. page starts at 1; page_size default 20, max 100; total always reflects the filters.

The three hard endpoints

These are where the exercise is decided. The contract defines the behaviour; working out how to get a database to do it is your job.

Department summary. Logs reference employees by emp_code, but the department lives on the employee. Headcount must include people with no logs and exclude people who have not joined yet. The average is over records, not an average of averages.

Late leaderboard. Ties share a rank and the next rank is skipped (1, 2, 2, 4). limit is applied after ranking. Tied rows are ordered by emp_code. Sorting, limiting and using the array index as the rank is the obvious approach, and it is wrong.

Department trend. Exactly one row per calendar day in the range, including weekends and days with no records, each with a moving average over the preceding window. The first rows have a shorter window. The work is done in the database, not in a Python loop.

Read app/main.py as if a teammate had opened a pull request. It runs and the happy path works. There are more than ten defects, spread across the helper functions and the endpoints. Some are visible within seconds; some only show up under concurrency, at scale, or with particular inputs.

Fix them, and list each one in REVIEW.md using the template: where it is, what is wrong, how you would notice it (an input, a test, or a symptom), and how you fixed it. 9. Part B: build the rest

Implement every endpoint marked "You" in section 7, exactly as openapi.yaml describes.

Analytics endpoints must be implemented as MongoDB aggregation pipelines, not by fetching documents and looping in Python.

Concurrency: two simultaneous punch-ins for the same employee and date yield exactly one 201 and the rest 409. Two simultaneous punch-outs yield exactly one 200. Concurrent regularizations must not silently lose each other's history entries.

Return correct status codes: 404 for missing resources (an unknown employee, or no record for that date), 409 for conflicts, 422 for validation failures (including a bad timestamp). A 500 is always a failed test.

Everything must be fast on a collection of about 100,000 attendance records. List and analytics endpoints must be backed by indexes.

Test your own work. We hand you only a tiny sample. Build your own test data with the awkward cases the rules describe: employees with no logs, ties, weekend records, a mid-month joiner, an overnight shift, a missing weekday. A pass on the sample is not a pass.

10. Part C: prove it and explain it

The explain endpoint

Implement GET /admin/explain/{endpoint} where endpoint is one of attendance_list, employee_monthly, department_summary, late_leaderboard, department_trend. It runs MongoDB's explain with executionStats verbosity on that endpoint's main query or pipeline, built the same way the real endpoint builds it (same filters, sort and pagination), and returns the raw output. It accepts the same query parameters as the endpoint it explains. We check that the plan uses an index scan (IXSCAN) and contains no collection scan (COLLSCAN), against the 100,000-record dataset.

DECISIONS.md

Answer the five questions in the template in your own words, about 150 to 200 words in total: which indexes you created and why; what exactly happens when two identical punch-ins arrive at the same instant; what your leaderboard returns for a tie at the cutoff; how your department summary counts employees with no logs; and what you would change for 100 times the data. We start the follow-up conversation from this file.
